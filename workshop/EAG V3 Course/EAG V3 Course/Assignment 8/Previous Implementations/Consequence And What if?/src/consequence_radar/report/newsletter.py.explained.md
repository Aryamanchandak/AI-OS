# `report/__init__.py`

Generates the final `NewsletterReport` from a compiled `ReportContext` via an LLM call, validates the result against structural and editorial rules (including the word-count bounds), and renders the accepted report to plain markdown. This is the last stage of the pipeline.

**`write_report(run_id, context, model, min_words, max_words) -> tuple[NewsletterReport, list[str]]`** is the main entry point. It calls `model.generate(run_id=run_id, stage="newsletter", prompt_name="report/newsletter_writer.md", prompt_data=context.model_dump_json(), schema=NewsletterReport, model_tier="report")` where `model: ModelClient` is the `providers.model` protocol (import noted, not deep-dived here). Concretely (per `providers/model/__init__.py`, read only to trace this wiring): `generate` resolves `prompt_name` via `load_prompt`, which reads `src/consequence_radar/report/newsletter_writer.md` from disk relative to the project root, takes its full text as the model instruction, and pulls a version string off the file's first-line `<!-- version: N -->` comment. It then sends `f"{instruction}\n\n<INPUT_DATA>\n{prompt_data}\n</INPUT_DATA>"` to the model, i.e. the entire prompt markdown followed by the full JSON-serialized `ReportContext`, and constrains the response to the `NewsletterReport` schema (so **the return value of `model.generate` is already a structured, schema-validated `NewsletterReport` object, not a raw string** — the "report" the LLM emits is a `headline`/`dek`/`why_this_matters`/`article_markdown`/`central_case_summary`/`key_assumptions`/`what_changes_the_view`/`source_ids_used` bundle, of which `article_markdown` is the actual long-form newsletter body). `write_report` then immediately runs `validate_report(report, context, min_words, max_words)` and **returns the tuple `(report, errors)`** — it does not raise on validation failure and does not filter/reject a bad report itself; the caller (a pipeline stage, not in this file) decides what to do with a non-empty `errors` list. This is exactly where `Settings.report_min_words`/`report_max_words` come in: they are not read from `Settings` inside this file at all — `write_report` takes them as plain `min_words`/`max_words` parameters, so the caller must be the one pulling `settings.report_min_words`/`settings.report_max_words` and passing them through. **The actual word-count check happens in `validate_report`, in this file**, not in `report_context` or the model layer.

**`validate_report(report, context, min_words, max_words) -> list[str]`** runs six independent checks and accumulates human-readable error strings (does not raise; empty list means valid):
1. `word_count(report.article_markdown)` — counts `\b[\w'’-]+\b` regex matches (a simple word-boundary count, not a tokenizer) and checks it falls in `[min_words, max_words]` inclusive.
2. Every `[Sxx]`-shaped citation marker in `article_markdown` (matched case-insensitively by `MARKER = re.compile(r"\[[Ss]\d+\]")`, normalized to uppercase) must correspond to a real `context.sources[].id`. The header comment explains this regex was deliberately narrowed from "any bracketed word starting with S" — the old pattern falsely flagged ordinary prose like `[SEBI]` or `[Sensex]` as an invented citation.
3. Every ID in `report.source_ids_used` (uppercased) must also be a real source ID.
4. Every string in `report.key_assumptions` must, after whitespace-collapsing (`_collapse`, so line-wrapping differences don't count as a mismatch), exactly match some `context.assumptions[].statement` — i.e. the model is not allowed to paraphrase assumptions, only copy them verbatim.
5. `why_this_matters` and `central_case_summary` must each be at least 8 words, else flagged as "not substantive."
6. `what_changes_the_view` must be non-empty, and `article_markdown` must not match any of four hardcoded `PROHIBITED` regexes (case-insensitive): "buy/sell/hold [the] stock/shares", "investors/readers should buy/sell/hold/purchase", "we recommend", "price target" — a compliance guardrail against the report reading as investment advice.

**`export_markdown(report) -> str`** is a trivial renderer: `f"# {headline}\n\n*{dek}*\n\n{article_markdown}\n"`. It does not include `why_this_matters`, `central_case_summary`, `key_assumptions`, `what_changes_the_view`, or `source_ids_used` — those structured fields exist on `NewsletterReport` for validation and presumably for a UI/API consumer to render separately, but this particular function only surfaces headline/dek/body as flat markdown.

Non-obvious: `write_report` never checks `errors` itself, so a caller that ignores the second tuple element would silently ship an invalid report (wrong word count, hallucinated citation, paraphrased assumption, or prohibited advice language) — validation is opt-in by construction, not enforced by this module.
