# `graph/initial_graph_builder.md`

A 5-line LLM prompt (plus a `<!-- version: 1 -->` tag on line 1) that instructs the model to construct a brand-new `CausalGraph` from a single news seed. It is the prompt behind the very first graph in every run.

**Role in the pipeline:** invoked exclusively from `build_initial_graph()` in `graph/__init__.py`, immediately after seed selection (`select_candidate`) and before any research/evidence-gathering cycle begins. It runs at most twice per run — once for the initial attempt (`stage="initial_graph"`) and, only if that graph fails `validate_graph`, once more for a repair attempt (`stage="initial_graph_repair"`, `retry_count=1`). There is no research context, prior graph, or claims available at this point — the graph is a hypothesis to be tested by later stages, not yet evidence-grounded.

**Expected input:** the prompt text refers to "the selected supplied-news premise" — concretely this is `seed.model_dump_json()`, the full JSON of the selected `Candidate`/seed object, passed as the `<INPUT_DATA>` block appended after the instruction text (see `providers/model/__init__.py generate()`: `f"{instruction}\n\n<INPUT_DATA>\n{prompt_data}\n</INPUT_DATA>"`). On the repair attempt, the input is instead `{"rejected_graph": <the invalid CausalGraph as JSON>, "validation_errors": [...]}` — the prompt text itself makes no distinction between these two cases; the difference is entirely on the caller side (same prompt file, different `prompt_data` payload and `stage` label).

**Demanded output format:** the prompt text never mentions JSON, a schema, or field names — it only describes the content requirements in prose (exactly one active `news_seed` root, every edge needs mechanism/confidence/direction/time lag/conditions/evidence status, no invented numbers or sources, `assumption_only` when evidence is absent, at least one terminal node must be India-tagged, no direct news-to-stock-price edge, no cycles, "Return version 1"). The actual output *shape* — a `CausalGraph` object matching the pydantic schema (`nodes`, `edges`, `assumptions`, `estimates`, `feedback_warnings`) — is enforced entirely in code, via `schema=CausalGraph` passed to `model.generate()`, which sets `response_json_schema=schema.model_json_schema()` on the Gemini call. The prompt's one explicit format instruction, "Return version 1," is actually redundant/unenforced by the model: `build_initial_graph()` overwrites whatever `version` the model returns with a hardcoded `1` via `model_copy(update={"version": 1})` regardless.

**Downstream consumer:** the raw model output is validated (`schema.model_validate(payload)`) inside `GeminiModelClient.generate`, so a structurally malformed response never reaches this prompt's caller — only a fully-typed `CausalGraph` does. `build_initial_graph()` in `graph/__init__.py` then force-sets `version=1` and runs `validate_graph()` (the semantic checks the prompt asks for in prose — DAG-ness, single seed, India reachability of terminals is *not* required at this stage since `require_indian_path` is left `False` here). If that fails once, the repair round-trips through this same prompt file before giving up and raising `GraphValidationError`. The resulting graph becomes `run["graph"]` (saved via `repo.save_artifact(run_id, "graph", graph, version=graph.version)` in `pipeline/__init__.py`) and is the seed for every subsequent `graph_patcher.md` call in the research loop.
