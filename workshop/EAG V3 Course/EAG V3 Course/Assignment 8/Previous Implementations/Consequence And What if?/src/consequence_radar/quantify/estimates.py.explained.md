# `quantify/__init__.py`

Pure-arithmetic helpers that turn pairs of `Estimate` ranges into new derived `Estimate`s — interval multiplication, currency conversion (built on the same multiplication), and a simple sensitivity band. No model calls, no I/O; this is the deterministic math layer that something upstream (a "quantify" pipeline stage, not in this file) invokes once it has decided which two estimates to combine and why.

**`multiply_range(*, estimate_id, metric, left, right, unit, period=None, currency=None, caveat, assumptions=None) -> Estimate`.** Requires both operands to have `low` and `high` set (raises `EstimateError` otherwise — a directional-only or centralonly estimate can't be multiplied this way). Computes all four corner products (`low*low, low*high, high*low, high*high`) under `decimal.localcontext(prec=28)` and takes `min`/`max` as the new `low`/`high` — this is interval arithmetic, not error propagation or a Monte Carlo method, and it implicitly assumes both inputs are non-negative or at least that the four corners bound the true product range (true for real intervals, but note it does not special-case negative values beyond what min/max naturally handles). `central` is `left.central * right.central` when both are present, else the midpoint of the derived range. There's a defensive clamp: if that central falls outside the just-computed `[low, high]` (possible when an input's own `central` isn't actually between its own `low`/`high` — nothing enforces that at the `Estimate` model level), it's clamped into range so the result is never self-contradictory. Output is `estimate_type="derived_range"`, `formula="{left.id} * {right.id}"`, `input_estimate_ids=[left.id, right.id]` — full lineage back to the two source estimates is preserved on the object, per `Estimate`'s own validator requiring `formula` and `input_estimate_ids` for any `derived_range`.

**`convert_currency(source, *, estimate_id, fx, target_currency) -> Estimate`** is `multiply_range` specialized for FX: requires `source.currency` to be set and `fx.low`/`fx.high` to be present (raises `EstimateError` naming exactly what's missing — the comment notes this used to silently guard on `fx.central` instead, which let an FX estimate with only a central value fall through to a confusing "range multiplication requires low and high" error from inside `multiply_range` rather than the real problem). It calls `multiply_range(source, fx, ...)`, so the underlying math is identical to any other range multiplication; the only currency-specific parts are the input validation and an auto-generated caveat string (`"Converted from {source.currency} using {fx.id}; original preserved separately"`).

**`sensitivity(base, coefficient, change=Decimal("0.10")) -> dict[str, Decimal]`** requires both `base.central` and `coefficient.central` (raises `EstimateError` otherwise) and returns three numbers keyed `"lower_input"`, `"central"`, `"higher_input"` — `base.central * coefficient.central` scaled down/up by `±change` (default ±10%) applied to the *product*, not to the base input alone. It returns a plain `dict[str, Decimal]`, not an `Estimate` — unlike the other two functions, this one doesn't produce a persisted, lineage-tracked object; callers presumably fold it into a narrative or a separate estimate themselves.

All three functions operate exclusively on `decimal.Decimal` (never float), matching `Estimate.low/central/high: Decimal | None` in the model — this is deliberate precision control appropriate for financial figures. `EstimateError` is a plain `ValueError` subclass, so callers that only catch `ValueError` still work, but nothing in this file catches or logs these errors itself — a missing range anywhere upstream surfaces as an uncaught exception unless a caller wraps it.
