# `src/consequence_radar/providers/model/test_model.py` — explained

Unit test suite for `GeminiModelClient.generate()` (defined in the sibling `__init__.py`). It never touches the real `google-genai` SDK or network — every test builds a `GeminiModelClient` instance by hand, wiring in lightweight stand-ins for the SDK's `client.models` object, the response objects it returns, and the `UsageLedger`. This makes the suite fast and deterministic, but it also means it is entirely a test of this module's *response-handling logic* (JSON parsing, schema validation, retry/fail-fast branching, audit records) — none of it exercises real Gemini API behavior, auth, or `GeminiModelClient.__init__` itself.

## Test scaffolding

- **`StubLedger`** (L14-23): a minimal stand-in for `metering.UsageLedger`. `guard_external_call()` just increments a counter (never raises `BudgetExceeded`, so no test exercises budget-exhaustion behavior inside `generate()`); `record(input_tokens, output_tokens)` stores the last-seen pair in `self.recorded`. Because it never raises, none of these tests verify what happens when the ledger's budget guard actually trips mid-retry — that's an untested interaction between `metering` and this module.

- **`response(text, *, finish_reason="STOP", prompt_tokens=7, output_tokens=3, thinking_tokens=0)`** (L26-42): builds a `SimpleNamespace` shaped like the real `google.genai` response object — `candidates[0].content.parts` (a list with one part carrying `.text` and `.thought=False`, or an empty list if `text is None`, simulating a body with zero parts), `candidates[0].finish_reason` (itself a `SimpleNamespace(name=...)`, mimicking the SDK's real enum-with-`.name` shape that `_enum_name` in the source module is written to handle), `prompt_feedback=None`, a top-level `.text` fallback attribute, and `usage_metadata` with the three token counts. This directly targets `response_text()`'s part-walking logic and the usage-extraction code in `generate()`.

- **`StubModels`** (L45-56): stands in for the real SDK's `client.models`. Constructed with one or more canned `response(...)` objects; `generate_content(*, model, contents, config)` records every `config` object it was called with (so tests can inspect what was actually sent to the "API," e.g. `response_json_schema`, `temperature`, `automatic_function_calling`) and returns responses in order, but clamps the index so that once the canned responses run out, it keeps returning the last one — this only matters for the two-canned-response retry test, where it drives attempt 1 with the first response and attempt 2 with the second.

- **`make_client(models, ledger, on_call=None, max_output_tokens=32_768)`** (L59-70): constructs a `GeminiModelClient` via `object.__new__(GeminiModelClient)`, deliberately bypassing `__init__` (and therefore the `settings.api_key` check and the `google.genai.Client(...)` construction) — it hand-assigns `.settings` (a `SimpleNamespace` with `fast_model`/`reasoning_model`/`report_model` all set to `"gemini-test"`, plus `max_output_tokens`), `.ledger`, `.on_call`, and `.client = SimpleNamespace(models=models)`. This is why the suite needs no API key and no network: it tests `generate()` as a pure function of its collaborators.

- **`generate(client)`** (L73-80): a fixed-argument wrapper calling `client.generate(run_id="run-1", stage="candidate_selection", prompt_name="candidate_selector.md", prompt_data="{}", schema=CandidateSelection)` — every test in the file reuses this exact call, varying only `client`. `CandidateSelection` (imported from `consequence_radar.models`) is the real production schema for the candidate-selection stage (`{"candidates": [...]}`), so schema-validation tests exercise real Pydantic validation errors, not a toy schema.

- **`stub_prompt` fixture (autouse)** (L83-88): monkeypatches `consequence_radar.providers.model.load_prompt` to always return `("Select candidates.", "test")`, so no test depends on real `.md` prompt files existing on disk or on prompt-version-comment parsing — `load_prompt`'s own file-reading/version-stripping logic is therefore untested here (it isn't covered anywhere in this file).

## What each test verifies

**`test_generate_uses_native_json_schema_for_dictionary_fields`** (L91-101): the core "happy path plus schema mechanics" test. Feeds a valid empty-candidates JSON body, asserts the returned object is a `CandidateSelection`, and — importantly — inspects the actual `GenerateContentConfig` passed to the stub: `response_schema is None` (confirming the code path uses `response_json_schema`, not the SDK's native Pydantic conversion) and that `response_json_schema["$defs"]["CandidateSeed"]["properties"]["grades"]["additionalProperties"]["enum"]` equals `["low", "medium", "high"]` — this directly verifies the reasoning documented in the source (L107-110 of `__init__.py`): that `dict[str, Grade]`-typed fields survive schema conversion correctly only via the JSON-Schema path. Also checks `automatic_function_calling.disable is True` and that `ledger.recorded == (7, 3)` (the default `prompt_tokens=7, output_tokens=3` from the `response()` helper), confirming token usage is threaded through to the ledger correctly.

**`test_generate_parses_a_fenced_body`** (L104-107): wraps the JSON body in Markdown triple-backtick fences (` ```json ... ``` `) and confirms it still parses — this is the direct test of the `_FENCE` regex / `decode_payload()` stripping logic, covering a real-world Gemini quirk where the model sometimes wraps JSON output in a code fence despite `response_mime_type="application/json"`.

**`test_a_transient_bad_body_is_retried_once`** (L110-118): supplies two canned responses — first `"not json at all"`, second a valid body — and confirms the call ultimately succeeds, that exactly two `generate_content` calls were made (`len(models.configs) == 2`), that the audit callback fired twice with `retry_count` `0` then `1`, and that the first audit record's `error` field mentions "not valid JSON". This is the single test proving the one-retry-on-bad-JSON behavior actually works end-to-end, including that `retry_count` increments correctly via the `retry_count + offset` arithmetic in the source.

**`test_truncated_output_fails_fast_without_burning_a_retry`** (L121-137): the fail-fast branch test, and arguably the most important edge case in the file given the source module's explicit design comment about not retrying `MAX_TOKENS`. Supplies a single truncated-looking response (`'{"candidates": ['`, `finish_reason="MAX_TOKENS"`, `thinking_tokens=2400`) and asserts: only **one** `generate_content` call happened (no retry attempted); the raised `ModelResponseError`'s message contains both the stage-prefixed summary and the specific "truncated at max_output_tokens=32768 after 2400 thinking tokens" detail; `.detail["finish_reason"] == "MAX_TOKENS"`, `.detail["thinking_tokens"] == 2400`, and `.detail["response_tail"]` equals the full (short) truncated body; and the audit callback fired exactly once. This test is the regression guard for the cost/latency optimization documented at L165-171 of the source — if someone "fixed" the code to retry on `MAX_TOKENS` like other failures, this test would catch it via the `len(models.configs) == 1` and `len(calls) == 1` assertions.

**`test_configured_budget_is_clamped_to_the_api_ceiling`** (L140-143): passes `max_output_tokens=OUTPUT_TOKEN_CEILING * 4` into `make_client` and confirms the config actually sent to the stub has `max_output_tokens == OUTPUT_TOKEN_CEILING` (65,536) — verifies the `min(settings.max_output_tokens, OUTPUT_TOKEN_CEILING)` clamp in the source (though in the real system, `Settings.max_output_tokens` is already Pydantic-bounded to `<= 65_536`, so this clamp is mostly defense-in-depth; this test proves the defense-in-depth actually works if that invariant is ever violated, e.g. by a stub/test settings object like this one).

**`test_empty_body_reports_the_finish_reason`** (L146-149): passes `text=None` to `response()` (which produces an empty `parts` list and `text=None`) with `finish_reason="SAFETY"`, and confirms the resulting error message contains "empty body (finish_reason=SAFETY)" — covers the empty-body branch and its `finish_reason` (and implicitly `block_reason`, though no test here sets `prompt_feedback` to a non-`None` blocked value, so the `block_reason` half of that message-building branch (L131, L134, L143 of the source) is not directly exercised by any test in this file).

**`test_schema_mismatch_names_the_offending_field`** (L152-157): supplies syntactically valid JSON that fails `CandidateSelection` validation (a candidate missing all required fields except `id`), and asserts the error message contains both "does not match CandidateSelection" and the dotted field path "candidates.0." — verifies `_validation_summary()`'s error-formatting logic actually surfaces which field failed, not just that validation failed.

**`test_transport_errors_are_audited_and_reraised`** (L160-169): defines a local `Boom` class whose `generate_content` raises `RuntimeError("404 NOT_FOUND")` unconditionally, confirms the same `RuntimeError` propagates out of `generate()` unchanged (via `pytest.raises(RuntimeError, match=...)`, not wrapped into `ModelResponseError`), and confirms the audit callback still fired once with `error == "404 NOT_FOUND"` before the re-raise. This is the test proving transport-level failures are *not* retried and are *not* converted into the module's own exception type — callers relying on `except ModelResponseError` to catch content problems will NOT catch a transport failure this way; they'd need a broader `except Exception` or a separate `except RuntimeError` if they want to handle both uniformly. No pipeline-stage caller inspected in this project's `select`/`graph`/`challenge`/`cases`/`report`/`research`/`pipeline` modules appears to distinguish between the two exception types when calling `generate()`, so in practice both surface the same way to the top-level pipeline runner.

## Coverage gaps (what this suite does NOT test)

- `GeminiModelClient.__init__` itself — the missing-API-key `ConfigurationError` path, and the real `genai.Client(...)` construction, are never exercised (every test bypasses `__init__` via `object.__new__`).
- `load_prompt()`'s real file-reading and `<!-- version: N -->` comment-stripping logic — always monkeypatched away.
- `response_text()`'s handling of a response with multiple parts, or parts where `thought=True` are mixed with real text parts (only ever tested with a single, non-thought part or zero parts).
- The `block_reason` half of the empty/invalid-body error message (`prompt_feedback.block_reason` is always `None` in the `response()` helper).
- Behavior when `UsageLedger.guard_external_call()` actually raises `BudgetExceeded` mid-`generate()` (the `StubLedger` never raises).
- A second attempt that *also* fails (the retry test's second canned response always succeeds; there's no test for "both attempts return bad JSON," though by reading the source this would raise the second `ModelResponseError` after two full attempts — untested but inferable from the loop structure).
- Any interaction with `model_tier` selection or a bad/unknown `model_tier` string (the `KeyError` risk noted in the source's doc) — every test uses the schema-level default (`"fast"`, implicitly, since `generate()` in this test file never passes `model_tier`).
