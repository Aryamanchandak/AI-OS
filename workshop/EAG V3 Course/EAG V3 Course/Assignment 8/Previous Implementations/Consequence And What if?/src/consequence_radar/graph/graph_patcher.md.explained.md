# `graph/graph_patcher.md`

A 5-line LLM prompt (plus a `<!-- version: 1 -->` tag) that instructs the model to propose an incremental **patch** — a list of add/update/reject operations — against an *existing* `CausalGraph`, rather than regenerating the graph wholesale ("Never regenerate the graph" is the prompt's explicit second sentence).

**Role in the pipeline:** unlike `initial_graph_builder.md`, this prompt is never loaded from `graph/__init__.py` at all — every call site lives in `pipeline/__init__.py`'s `Pipeline.run()`, always with `schema=GraphPatch`. It is used at three distinct points in a run:
1. Inside the research loop, once per research cycle (`stage="graph_patch"`), after `generate_tasks` and `extract_claims` have run for that cycle — the model is asked to fold the cycle's new evidence into the graph.
2. As a one-shot repair (`stage="graph_patch_repair"`, `retry_count=1`) if `apply_patch()` raises on the cycle's first patch — same prompt file, different `prompt_data` (includes the `rejected_patch` and `validation_errors`).
3. After the research loop, once, to specifically fill in missing quantification on Indian-equity terminal nodes (`stage="quantification_patch"`) — here the JSON payload includes a synthetic `"instruction"` key overriding what a bare graph+claims call would otherwise imply, telling the model exactly what gap to close ("add a sourced/derived estimate or an explicit directional_only estimate ... Do not invent numbers").

**Expected input:** the prompt text speaks generically of "supplied verified evidence" and instructs that IDs must be reused for updates/rejections and new unique IDs used for additions. Concretely, `prompt_data` is always a JSON object built by the pipeline, minimally containing `"graph"` (the current `CausalGraph.model_dump(mode="json")`) plus one of: `"tasks"` + `"claims"` (normal cycle), `"rejected_patch"` + `"validation_errors"` + `"claims"` (repair), or `"instruction"` + `"claims"` (quantification pass). The prompt text does not enumerate these keys explicitly — the caller controls exactly what evidence and framing accompanies the graph on each call.

**Demanded output format:** as with the builder prompt, no JSON/schema language appears in the prompt text at all; it is described entirely in prose (separate facts/forecasts/assumptions/inferences/estimates; a "supported" edge needs real supporting claim ids; "mixed" needs both support and contradiction; derived numbers need formula/input ids/units/period/assumptions/caveat; never invent sources/numbers/probabilities; preserve the India transmission path; return remaining research gaps, empty only when genuinely resolved). The structural shape — a `GraphPatch` with `operations: list[GraphOperation]`, `reason`, `evidence_ids`, `remaining_gaps` — is enforced purely via `schema=GraphPatch` / `response_json_schema` in `providers/model/__init__.py`, exactly as with the builder prompt.

**Downstream consumer:** the returned `GraphPatch` is passed to `apply_patch(graph, patch, settings)` in `graph/__init__.py`. Note a real bug there: any operation with `op` in `{"add_assumption", "update_assumption", "add_estimate", "update_estimate"}` — all things this prompt's own instructions explicitly ask the model to produce ("Derived numbers require formula, input estimate IDs...") — currently crashes `apply_patch` with `ModuleNotFoundError` because of a broken relative import (`from .models import Assumption` instead of `..models`; see `graph/__init__.py.explained.md`). In the pipeline this is swallowed by a broad `except Exception`, logged as an `invalid_graph_patch` artifact, and treated like an ordinary validation failure — triggering the repair call described above — but if the repair also proposes an assumption/estimate op it fails the same way and the cycle's patch is effectively dropped. `remaining_gaps` from whichever patch is ultimately applied feeds the loop's exit condition (`if not gaps: break`) and, at the end of the run, becomes part of `report_context`'s `known_gaps`.
