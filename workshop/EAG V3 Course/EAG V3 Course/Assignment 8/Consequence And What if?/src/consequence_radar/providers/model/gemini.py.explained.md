# `src/consequence_radar/providers/model/__init__.py` — explained

This is the single chokepoint through which every LLM-driven pipeline stage talks to Gemini. It defines the `ModelClient` protocol callers code against, the concrete `GeminiModelClient` implementation that wraps the `google-genai` SDK, and the JSON-decoding/schema-validation/retry machinery that turns a raw model response into a validated Pydantic object or a well-diagnosed failure. Nothing in this file knows what a "causal graph" or a "candidate seed" is — it is generic over any Pydantic `BaseModel` subclass passed in as `schema`.

## Who calls this and how

A grep across `src/consequence_radar` shows this module imported by seven sibling packages: `select`, `graph`, `challenge`, `cases`, `report`, `research`, and `pipeline` (which also imports the concrete `GeminiModelClient` to construct it). Every one of them imports only the `ModelClient` Protocol (L32-33), not the concrete class — `pipeline/__init__.py` is the sole place that constructs a `GeminiModelClient` and hands it down as a dependency, everywhere else takes `model: ModelClient` as a parameter. This is a clean dependency-injection seam: tests and other call sites can substitute a stub implementing the same `generate()` signature without touching `google.genai`.

The calling convention is identical everywhere: build a JSON string of context data (usually `some_pydantic_model.model_dump(mode="json")` or `.model_dump_json()`, sometimes a hand-built `json.dumps({...})` bundling a graph, claims, and other context), then call

```python
model.generate(
    run_id=run_id,
    stage="candidate_selection",           # a free-text label, used only for audit records and error messages
    prompt_name="select/candidate_selector.md",  # path relative to src/consequence_radar/
    prompt_data=payload,                    # a JSON string, becomes <INPUT_DATA> in the prompt
    schema=CandidateSelection,              # the Pydantic model the JSON reply must satisfy
    model_tier="reasoning",                 # optional: "fast" (default), "reasoning", or "report"
    retry_count=1,                          # optional: only used cosmetically for audit numbering on manual re-asks
)
```

and the call either returns an instance of `schema` or raises. Concrete examples pulled from callers: `select/__init__.py` calls with `schema=CandidateSelection` and no `model_tier` (defaults to `"fast"`); `graph/__init__.py` and `challenge/__init__.py` use `model_tier="reasoning"` for graph-building, patching, review, challenge, and adjudication; `report/__init__.py` uses `model_tier="report"` for the newsletter; `research/__init__.py` uses the default `"fast"` tier for gap analysis and claim extraction. `pipeline/__init__.py` additionally shows the "repair" pattern: when a first `generate()` call produces a structurally invalid graph/patch (caught by pipeline-level validation, not this module), it calls `generate()` again against the *same* prompt file with `rejected_graph`/`rejected_patch` plus `validation_errors` folded into `prompt_data`, and passes `retry_count=1` purely so the audit trail's `retry_count` field reflects that this is a second attempt at the same logical step — this module does not know or care that it's a repair, it's just another `generate()` call.

## `load_prompt(name: str) -> tuple[str, str]` (L36-41)

Resolves `PROJECT_ROOT / "src" / "consequence_radar" / name` and reads it as UTF-8 text. Prompt files live alongside the stage code that uses them (e.g. `select/candidate_selector.md`, `challenge/challenger.md`), each starting with an optional `<!-- version: N -->` comment on the first line; `load_prompt` strips that comment via `removeprefix`/`removesuffix` and returns `(text, version)`, defaulting version to `"1"` if the comment is absent. The version string is not used for any behavioral branching here — it's carried through purely so the `_audit` record can log which prompt revision produced a given output, which matters for debugging regressions after a prompt edit. Every prompt file inspected (`select/candidate_selector.md`, etc.) does start with `<!-- version: 1 -->`.

## `ModelClient` Protocol (L32-33)

A structural-typing contract with one method, `generate(...)`, matching `GeminiModelClient.generate`'s signature exactly. This is what every caller type-annotates against, which is why swapping in a test double or a future non-Gemini backend requires no changes to the seven calling modules.

## `GeminiModelClient` (L78-173)

### `__init__(self, settings: Settings, ledger: UsageLedger, on_call=None)` (L79-84)

Requires `settings.api_key` (a `Settings.api_key` property that resolves to `gemini_api_key or google_api_key`, both read from `.env`/environment by `pydantic_settings`) — raises `ConfigurationError` if neither is set, which is the only validation of API-key presence anywhere in this module. The `google.genai` import is deferred inside `__init__` rather than at module scope, presumably so importing this module (and therefore anything downstream, like `pipeline`) doesn't hard-require the `google-genai` package to be installed unless a real `GeminiModelClient` is actually instantiated — test code, for instance, never triggers this import because `make_client` in the test file bypasses `__init__` entirely via `object.__new__`. `ledger` is a `UsageLedger` from the sibling `metering` package — every `generate()` call is metered through it (see below). `on_call` is an optional callback of one argument (a `dict` audit record) invoked after every attempt, successful or not; it's the module's only structured observability hook — no logging module is used anywhere in this file.

### `generate(...)` (L90-173) — the core method

Call signature: `generate(self, *, run_id: str, stage: str, prompt_name: str, prompt_data: str, schema: type[T], model_tier: str = "fast", retry_count: int = 0) -> T`, where `T` is bound to `pydantic.BaseModel`. Returns a validated instance of `schema`, or raises `ModelResponseError` (subclass of `RuntimeError`, carrying a `.detail` dict which is the same audit record passed to `on_call`) if it never gets a schema-valid response, or re-raises whatever exception the SDK call itself throws (network errors, auth errors, etc. are not caught or wrapped — only *response content* problems are turned into `ModelResponseError`).

Step by step:

1. **Prompt assembly** (L92-94): loads the instruction text via `load_prompt`, resolves `model` by looking up `model_tier` in a hardcoded three-way dict against `self.settings.{fast_model,reasoning_model,report_model}` (an unrecognized `model_tier` string raises a plain `KeyError`, not a friendlier error — this is a real gap: a typo in a caller's `model_tier=` argument fails with a cryptic `KeyError` rather than naming the bad value). The final prompt sent to the model is simply `f"{instruction}\n\n<INPUT_DATA>\n{prompt_data}\n</INPUT_DATA>"` — a flat string concatenation, not a templating engine; there are no `{variable}` substitutions inside the `.md` files themselves; all "templating" is really just "instruction text + a fixed XML-ish wrapper around a JSON blob."

2. **Token budget** (L95): `budget = min(self.settings.max_output_tokens, OUTPUT_TOKEN_CEILING)`. `OUTPUT_TOKEN_CEILING` is a hardcoded module constant, `65_536` (L15), documented as "highest `max_output_tokens` the 2.5 and 3.x Gemini families accept." `Settings.max_output_tokens` defaults to `32_768` and is itself bounded `[1024, 65_536]` by a Pydantic `Field` constraint in `config/__init__.py`, so in practice this `min()` only bites if someone sets `MAX_OUTPUT_TOKENS` above the hard ceiling — the test `test_configured_budget_is_clamped_to_the_api_ceiling` exercises exactly this by constructing a `Settings`-like stub with `max_output_tokens=OUTPUT_TOKEN_CEILING * 4`.

3. **Retry loop, `for offset in range(2)`** (L98-171): this is a fixed two-attempt loop, not exponential backoff or unlimited retry — at most one retry, and only for certain failure modes (see below). Model name, temperature, and token budget are model-name-and-config *hardcoded per call*, not user-configurable per invocation beyond the tier selection: `temperature=0.1` is a literal on L112 with no parameter to override it, so every single call across the whole pipeline — candidate selection, graph building, adjudication, report writing — runs at the same low temperature.

   - `self.ledger.guard_external_call()` (L99) is called *before* each attempt, including the retry — this is the budget-enforcement hook into `metering.UsageLedger`. `guard_external_call` raises `metering.BudgetExceeded` if the run's wall-clock time or model-call count budget (from `Settings.max_wall_time_seconds` / `max_model_calls_per_run`) is exhausted; that exception is not caught here, so it propagates straight up through `generate()` to the pipeline, aborting the run. Note this means a single logical `generate()` call that needs its internal retry consumes *two* entries against the call budget, which `config/__init__.py`'s comment on `max_model_calls_per_run` explicitly accounts for ("plus room for a parse retry").
   - The actual SDK call (L102-119) uses `response_json_schema=schema.model_json_schema()` rather than the SDK's `response_schema=<pydantic class>` parameter — the comment (L107-110) explains this is because the Gemini Developer API rejects dict-valued `additionalProperties` (which Pydantic emits for `dict[str, SomeEnum]` fields, e.g. `CandidateSeed.grades: dict[str, Grade]`) when converting a Pydantic model directly, but accepts the same shape via the native JSON-Schema path. This is confirmed by `test_generate_uses_native_json_schema_for_dictionary_fields`, which asserts `config.response_schema is None` and inspects the raw JSON schema's `grades.additionalProperties.enum`.
   - `automatic_function_calling=types.AutomaticFunctionCallingConfig(disable=True)` (L117) is set purely to suppress an SDK warning log on every call — there is no tool/function-calling use anywhere in this module.
   - If `generate_content` itself raises (network failure, auth failure, HTTP error, malformed request, etc.), the exception is recorded into the audit dict as `error` (L121), the audit callback fires, and the exception is **re-raised immediately, uncaught, with no retry** (L120-123). So the two-pass retry loop only ever protects against *bad response content* (empty body, non-JSON body, schema mismatch) — transport-level failures get zero retries and propagate straight to the caller. `test_transport_errors_are_audited_and_reraised` confirms this exact behavior.

4. **Usage accounting** (L125-132): pulls `prompt_token_count`, `candidates_token_count`, `thoughts_token_count` off `response.usage_metadata` (all defaulting to `0` if missing/`None`), and calls `self.ledger.record(inp, out)` — note only input and output tokens are recorded into the ledger, not thinking tokens; thinking tokens are tracked only in the local audit record, not fed into cost/budget accounting. `finish_reason` and `block_reason` are extracted via `_enum_name` (L44-48), a small helper that copes with the SDK sometimes returning real enum members (which have a `.name` attribute) and sometimes plain strings (over "the wire", e.g. when reconstructed from JSON) — `str(getattr(value, "name", value))` handles both uniformly.

5. **Body extraction and JSON decoding** (L136-148): `response_text()` (L51-65) is a standalone helper that walks `response.candidates[*].content.parts[*]`, concatenating `.text` from every part that is *not* a "thought" part (Gemini's extended-thinking parts have `.thought = True` and would otherwise pollute the JSON payload). If no candidates/parts exist at all (stub payloads, or older SDK shapes), it falls back to `response.text`. If the resulting text is empty/whitespace-only, that's treated as a first-class failure mode with a message naming the `finish_reason` (and `block_reason` if Gemini's safety filter fired) — this is what `test_empty_body_reports_the_finish_reason` checks, using `finish_reason="SAFETY"`. If there is text, `decode_payload()` (L68-69) strips a leading/trailing Markdown code fence (regex `_FENCE`, L17: `\A\s*```(?:json)?\s*|\s*```\s*\Z`) before calling `json.loads`; the comment at L136-138 explains why this manual re-parse exists at all — the SDK's own `response.parsed` convenience field silently becomes `None` on a JSON decode failure without surfacing *why*, so this code re-does the decode itself specifically to capture the `JSONDecodeError` message.

6. **Schema validation** (L150-157): if JSON decoding succeeded, `schema.model_validate(payload)` is attempted; on `pydantic.ValidationError`, `_validation_summary()` (L72-75) builds a compact message from at most the first 3 field errors (`loc: msg`, joined with the dotted path, root errors rendered as `<root>`), plus a `(+N more)` suffix if there were more — see `test_schema_mismatch_names_the_offending_field`, which checks the message contains `candidates.0.` as the error's dotted location. On success, the audit callback fires with the clean record and the validated instance is returned immediately — this is the only return point in the whole retry loop.

7. **Retry decision** (L159-171): any problem (empty body, bad JSON, schema mismatch) is recorded into the audit dict (`error`, plus a `response_tail` of the response's last 400 characters for post-mortem debugging) and wrapped into a pending `ModelResponseError`, but the loop does **not** immediately raise it — unless `finish_reason == "MAX_TOKENS"`, in which case it `break`s out of the loop early, skipping the second attempt. The reasoning (commented at L165-171) is that a truncated generation at `temperature=0.1` will almost certainly reproduce identically on a re-ask, so retrying just burns a second model call and wall-clock time for no benefit, and would risk masking the real error behind a later `BudgetExceeded`. For any *other* problem (bad JSON, schema mismatch, generic empty body not caused by truncation), the loop continues to a second iteration with the same `contents`/`config` — this is a literal identical re-ask, no prompt modification, no backoff delay, just hoping for a better roll. If both attempts fail, `failure` (set on the first failing iteration, potentially overwritten by the second) is raised after the loop exits (L173).

### Free functions/exceptions used by callers or tests

- `ConfigurationError(RuntimeError)` (L20-21): raised only from `__init__` when no API key is configured.
- `ModelResponseError(RuntimeError)` (L24-29): carries `.detail`, the audit dict, so callers/tests can inspect `finish_reason`, `thinking_tokens`, `response_tail`, etc. without string-parsing the exception message.
- `response_text`, `decode_payload`, `load_prompt` are all module-level and imported directly by the test file, not just used internally — they're effectively part of this module's public surface even though nothing outside the test file imports them today (per the grep, no pipeline-stage module imports anything from this file besides `ModelClient` and, in one case, `GeminiModelClient`).

## Data-shape example

A concrete call from `select/__init__.py`:

- `prompt_name="select/candidate_selector.md"` → instruction text ending in "Return up to three CandidateSeed objects... Grade exactly these dimensions low/medium/high: ..."
- `prompt_data` → a JSON string of source news items
- `schema=CandidateSelection` (`src/consequence_radar/models/__init__.py:367`) → `{"candidates": [CandidateSeed, ...]}` where each `CandidateSeed` (same file, L116-127) has fields like `id`, `source_item_ids`, `reported_premise`, `factual_status`, `grades: dict[str, Grade]` (a dict of dimension name → `"low"|"medium"|"high"`), `rationale`, `weaknesses`, `selected`.
- The full prompt sent to Gemini is: `"<instruction text>\n\n<INPUT_DATA>\n{...news items json...}\n</INPUT_DATA>"`, with `response_json_schema` set to `CandidateSelection.model_json_schema()`.
- On success, `generate()` returns a live `CandidateSelection` Python object with validated `.candidates` list; on failure after two tries, callers see a `ModelResponseError` whose message reads like `"candidate_selection returned no usable structured response: the response JSON does not match CandidateSelection (candidates.0.grades: field required)"`.

## Notable gaps / hardcoded assumptions worth flagging

- `model_tier` is validated only by dict-lookup `KeyError`, not an explicit `Literal`/enum or a friendly error message naming the invalid tier.
- `temperature=0.1` is hardcoded with no per-call override, even for stages (e.g. report writing) that might benefit from different sampling settings.
- Transport/network errors get no retry at all — only content-shape problems do, and only once.
- The retry-vs-fail-fast branch is keyed on the literal string `"MAX_TOKENS"` matching whatever `_enum_name` extracts — if the Gemini SDK ever renames or restructures this enum, the fail-fast optimization silently stops firing (it would just fall through to a second, likely-also-truncated retry instead of erroring cleanly, so failure mode is "extra latency," not "broken").
- Thinking tokens (`thoughts_token_count`) are captured in the audit trail but never passed to `ledger.record`, so per-run cost/budget tracking (`UsageLedger`) is currently blind to thinking-token spend — only prompt and output tokens count toward whatever downstream cost reporting the metering package does.
- There is no explicit rate-limit handling (e.g. HTTP 429 backoff) — a rate-limit error surfaces as a generic transport exception and is re-raised uncaught, same as any other SDK exception.
