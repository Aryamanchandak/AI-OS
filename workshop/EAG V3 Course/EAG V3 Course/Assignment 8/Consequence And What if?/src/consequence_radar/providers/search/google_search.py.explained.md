# `providers/search/__init__.py`

Defines the pipeline's web-search boundary: a `SearchProvider` protocol and one concrete implementation, `GeminiGoogleSearchProvider`, which does not call a search API directly but instead asks a Gemini model to perform search-grounded generation via Google's built-in "grounding" tool (plus the URL Context tool, since a later change) and parses the citations back out. Mocked coverage lives in `providers/search/test_search.py`.

## Main entry points

### `class SearchResult` (frozen dataclass)
`url`, `title`, `snippet` (snippet defaults to `""`; the implementation below now populates it from grounding-support text — see below).

### `class SearchProvider(Protocol)`
Structural interface: anything with `.search(query: str, *, max_results: int) -> list[SearchResult]` satisfies it. This is what `research/__init__.py` and `pipeline/__init__.py` type against, so a test double or alternate provider can be substituted without inheriting from anything.

### `class GeminiGoogleSearchProvider`
The only implementation. This is **not** a wrapper around a dedicated search API (no Bing/SerpAPI/Google Custom Search key) — it is a Gemini `generate_content` call with Google Search grounding turned on as a tool, and the "search results" are the grounding citations Gemini attaches to its answer.

**Construction** (`__init__(settings, ledger, on_call=None, run_id_getter=None)`):
- Raises `RuntimeError("GEMINI_API_KEY or GOOGLE_API_KEY is required for grounded search")` immediately if `settings.api_key` is falsy (that property reads `gemini_api_key or google_api_key` from `Settings`) — fails fast at construction, not at first `.search()` call.
- Imports `google.genai` lazily, inside `__init__`, rather than at module top — likely to avoid a hard dependency on the `google-genai` package for code paths that never construct this class.
- Builds a `genai.Client(api_key=settings.api_key)` and stores it.

**`search(query, *, max_results)`**:
1. Calls `self.ledger.guard_external_call("search")` first — this is a budget check against `UsageLedger` (see `metering/__init__.py`), not a rate limiter in the throttling sense. It raises `BudgetExceeded` if the run's wall-clock budget (`max_wall_time_seconds`) has elapsed, or if the run's search-call count has hit `max_searches` (which defaults to the model-call cap `max_model_calls_per_run` unless `pipeline/__init__.py` passes a separate `max_search_queries_per_run` — it does, per the `UsageLedger(..., settings.max_search_queries_per_run)` construction seen in `pipeline/__init__.py`). If the guard passes, it increments an internal counter; there's no backoff/sleep/retry here — it's a hard cap that raises once exceeded.
2. Calls `self.client.models.generate_content(...)` with:
   - `model=self.settings.fast_model` — hardcoded to whatever `Settings.fast_model` is (default `"gemini-2.5-flash"`), not a search-specific model setting.
   - `contents=f"Find up to {max_results} sources for this research query and briefly describe relevance: {query}"` — the "search" is entirely prompt-driven; there's no structured query API, no filters, no locale/date params.
   - `config=types.GenerateContentConfig(tools=tools, automatic_function_calling=types.AutomaticFunctionCallingConfig(disable=True))` — `tools` always includes `types.Tool(google_search=types.GoogleSearch())` and, when `settings.enable_url_context_search` is true (the default), also `types.Tool(url_context=types.UrlContext())`, letting the model open each candidate page while describing relevance. Live-API testing confirmed tool use (either tool) is rejected by the API when combined with `response_json_schema`, so this call remains hand-parsed plain text, never structured output — deliberately, since structured output is exactly the mechanism used elsewhere for a claim's `exact_passage`. Automatic function-calling loops stay disabled (single-shot call).
3. Records token usage: pulls `prompt_token_count`/`candidates_token_count`/`tool_use_prompt_token_count` off `response.usage_metadata` (defensively, via `getattr(..., None)` and `or 0` guards — a missing or malformed usage object degrades to zero-cost rather than raising). URL-context-retrieved content is billed under `tool_use_prompt_token_count`, separate from `prompt_token_count`, so it's added into `input_tokens` before `self.ledger.record(input_tokens, output_tokens)` so the cost ledger reflects the real cost.
4. If an `on_call` callback was supplied, invokes it with a dict describing the call: `run_id` (from `run_id_getter()` if provided, else `""`), `stage="grounded_search"`, `model_name`, `prompt_version="google-search-1"` (hardcoded literal, not derived from anything), `input_tokens`/`output_tokens` (input already includes `tool_use_prompt_token_count`), `tool_use_prompt_token_count` (also reported standalone for visibility), `retry_count=0` (always `0` — there is no retry logic in this method at all; a transient API failure is not retried here). This looks like a hook for cost/usage telemetry recorded per pipeline stage.
5. Parses results out of `response.candidates`: for each candidate, reads `candidate.grounding_metadata.grounding_chunks` and `candidate.grounding_metadata.grounding_supports`. Each support carries `segment.text` (the model's relevance text for a citation) and `grounding_chunk_indices` (which chunk(s) it's about); these are grouped by chunk index first, then for each chunk with a `.web.uri`, a `SearchResult(uri, title_or_uri, snippet)` is built where `snippet` is the space-joined support texts for that chunk's index (`""` if no support named it). `getattr` is used throughout this parsing (`grounding_metadata`, `grounding_chunks`, `grounding_supports`, `web`, `uri`, `title`, `segment`) with `None`/`[]` fallbacks, so a response with no grounding data, a missing `web` field, or an unexpected shape simply yields zero results/empty snippets rather than raising — this is a silent-failure path: a malformed or grounding-less response looks identical to "no relevant sources found." Snippets are not read anywhere yet — `research/__init__.py`'s `retrieve_for_tasks` only uses `hit.url` and `hit.title` off each `SearchResult` — so this is a populated-but-unconsumed field for now. Regardless, they never become a claim's `exact_passage` — that always comes from `providers/fetch/__init__.py`'s own SSRF-guarded fetch, kept entirely separate from this model-mediated text.
6. Deduplicates by URL (first occurrence wins, order-preserving) and truncates to `max_results`.

## Non-obvious logic and hardcoded values
- Model used for search is `settings.fast_model`, shared with other "fast" LLM stages elsewhere in the pipeline — there's no dedicated "search model" setting.
- `prompt_version` string `"google-search-1"` is a hardcoded literal in the telemetry payload, seemingly a manually-maintained version tag for this prompt shape (the prompt itself is an f-string, not a file-based template, unlike other stages that reference `prompt_name="....md"` — worth noting this stage's "prompt" is inline code, not a versioned template file).
- `retry_count` is always reported as `0` in telemetry regardless of what actually happened — there is no retry mechanism in this class, so the field is structurally always zero, not just usually.
- No explicit HTTP timeout is set here; whatever timeout behavior exists comes from the `google-genai` SDK's own defaults, not from `Settings.fetch_timeout_seconds` (that setting belongs to `providers/fetch`, unrelated to this module).
- No handling of `google.genai` exceptions (auth failure, rate limit, network error) — none are caught; they propagate directly out of `search()` to the caller.
- Result ordering follows Gemini's grounding-chunk order, not any relevance score exposed to the caller.

- `src/consequence_radar/pipeline/__init__.py` — imports both `GeminiGoogleSearchProvider` and `SearchProvider`, and is the sole place that constructs the concrete provider: `self.search = search or GeminiGoogleSearchProvider(settings, self.ledger, on_call=self._record_model_call, run_id_getter=lambda: self._active_run_id)`. This is also where the `UsageLedger` is built with `settings.max_search_queries_per_run` as its search-specific cap, and where `PageFetcher` is wired in alongside it — `search` and `fetch` are constructed together and passed as a pair into `retrieve_for_tasks`.
- No import of `providers.search` was found in `report/__init__.py` — an earlier grep hit there was a false positive from `re.search`/a comment referencing "providers/search.py", not an actual import.

Depends on: `consequence_radar.config.Settings` (`api_key`, `fast_model`, and indirectly `max_search_queries_per_run` via the caller), `consequence_radar.metering.UsageLedger` (budget guard + usage recording), and the third-party `google-genai` SDK (imported lazily, only inside this class).
