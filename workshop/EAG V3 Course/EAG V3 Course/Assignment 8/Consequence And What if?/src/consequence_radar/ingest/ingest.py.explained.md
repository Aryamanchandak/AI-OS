# `ingest/__init__.py`

Turns a caller-supplied `NewsBatch` of raw URLs into deduplicated, content-bearing `DiscoveryExtract` records. This is the front door of the pipeline: nothing upstream of this module reads news, and everything downstream (`deduplicate`, `select`) works off `DiscoveryExtract`, not `NewsItem`.

Raw input is not RSS or a file path — it's a `NewsBatch` (from `consequence_radar.models`), a Pydantic object the caller must already have constructed: `batch_id`, a list of 1-100 `NewsItem` (each just an `HttpUrl` plus optional `headline`, `snippet`, `publisher`, `published_at`, `topic`), `target_market` (fixed to `"indian_equities"`), and `report_audience`. So "ingest" here means "normalize and lightly fetch a list of already-discovered URLs," not "go find news" — discovery/search is someone else's job (`providers/search`), this module just processes what it's handed.

Two entry points:

**`normalize_batch(batch) -> NewsBatch`.** For each item: canonicalizes the URL via `providers.fetch.normalize_url` (strips tracking params etc.), drops the item if the canonical URL was already seen in this batch (dedup by URL, not content), and overwrites `item.id` with `stable_item_id(canonical)` regardless of whether the caller supplied one. `stable_item_id` is `"N" + sha256(url)[:12].upper()` — a deterministic 12-hex-char ID keyed only on the canonical URL, so the same URL gets the same node ID across separate runs and restarts. The comment in the code is explicit about why: upstream-supplied IDs are untrusted metadata, not stable keys. Returns a new `NewsBatch` with the same `batch_id`/`target_market`/`report_audience`/`requested_at` but a shorter, deduplicated, ID-stamped `items` list.

**`pre_read(batch, fetcher, max_chars=8000, guard=lambda: None) -> list[DiscoveryExtract]`.** For each item (note: iterates `batch.items` directly, not a normalized batch — callers are expected to call `normalize_batch` first if they want dedup/stable IDs applied before fetching):
- Calls `guard()` before each item — a hook with no default behavior, presumably wired elsewhere to a budget/rate limiter or cancellation check. Nothing here inspects its return value; it exists purely to be called (or to raise).
- If `headline` and `snippet` are both present and their concatenation is >= 240 characters, it skips fetching entirely and builds the extract straight from the supplied metadata (`fetched=False`). This is a real optimization/cost-control: a sufficiently detailed snippet is trusted as "good enough" text without spending an HTTP fetch.
- Otherwise it calls `fetcher.fetch(canonical)` (a `providers.fetch.PageFetcher`), joins the supplied headline/snippet with the fetched body text, truncates to `max_chars`, and sets `fetched=True`. Publisher falls back to the fetched page's hostname if not supplied.
- Any exception from `fetcher.fetch` (network error, `UnsafeUrl`, parse failure, etc.) is caught broadly (`except Exception`) and turned into a `DiscoveryExtract` with `fetched=False` and `failure_reason=str(exc)` — a single bad URL never aborts the batch, it just produces a thin, unfetched extract carrying the error message forward for visibility.

Non-obvious bits: `max_chars=8000` is a hard truncation on the extract text (independent of the 80,000-char cap already inside `PageFetcher.fetch`), so downstream stages only ever see the first 8k characters of a page regardless of article length. `item.id` used in `pre_read` falls back to `stable_item_id(str(item.url))` if the item still has no ID, which matters if `pre_read` is ever called on a batch that skipped `normalize_batch`.

Connects to `providers.fetch` for `PageFetcher`/`normalize_url`/`UnsafeUrl` (not documented here — out of scope), and downstream to `deduplicate.deduplicate`, which consumes exactly the `list[DiscoveryExtract]` this module produces.
