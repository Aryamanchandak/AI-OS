# `models/test_models.py` — explained

This is the (small) test suite for `models/__init__.py`. It contains a single test function that covers two unrelated behaviors of the models module, both defensively important given how the models get used (as validation gates for LLM-generated JSON and as carriers of numeric estimates that eventually reach a published report).

`test_batch_cardinality_and_decimal_preservation` does two things under one name:

First, `pytest.raises(ValidationError): NewsBatch(items=[])` confirms that `NewsBatch.items`'s `Field(min_length=1, max_length=100)` constraint is actually enforced — an empty batch is rejected rather than silently accepted. This matters because a `NewsBatch` is the entry point of the whole pipeline; if an empty batch could be constructed, downstream stages would need to handle "run started but there was nothing to process" as a valid case instead of that possibility being closed off at the model boundary.

Second, it constructs a valid `Estimate` with `estimate_type="derived_range"`, `low=Decimal("0.1")`, `central=Decimal("0.2")`, `high=Decimal("0.3")`, a `formula`, `input_estimate_ids=["A","B"]`, and a `caveat`, then asserts `estimate.model_dump_json().count("0.1") == 1`. This exercises two things at once: implicitly, that the model construction itself satisfies `Estimate`'s two validators (`ordered_range`, since `0.3 >= 0.1`, and `lineage_rules`, since a `derived_range` estimate here does supply both `formula` and `input_estimate_ids`) — though the test never asserts the *failure* path of either validator, only that valid input succeeds. Explicitly, the `count("0.1") == 1` assertion checks that `Decimal` values round-trip through `model_dump_json()` as exact decimal literals rather than being coerced through `float` (which would risk producing something like `0.1` becoming `0.10000000000000001` or colliding with a stringified rendering elsewhere in the JSON). This is the reason the models file uses `Decimal` rather than `float` for `Estimate.low`/`central`/`high` in the first place — the test is effectively a regression check for that precision-preservation guarantee, since a `float`-based implementation could easily fail this exact assertion.

What the test does *not* cover: the `all_dimensions` validator on `CandidateSeed.grades`, the `lineage_rules` failure paths (a `source_value` estimate missing `source_claim_ids`, or a `derived_range` missing `formula`/`input_estimate_ids`), the `ordered_range` failure path (`high < low`), or any of the `StrictModel` `extra="forbid"` behavior. Those are plausible gaps if a future change to the model's validation logic needs a regression test.
