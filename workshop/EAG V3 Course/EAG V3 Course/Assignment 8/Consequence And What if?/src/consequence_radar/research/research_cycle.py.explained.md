# `research/__init__.py`

Implements the "gap → search → fetch → extract" cycle: given a causal graph, decide what needs sourcing, run web searches, fetch and truncate the pages, then extract verifiable atomic claims from them. Three functions, run in sequence once per research cycle by the pipeline (which repeats the cycle up to some cap, feeding fresh graph state back in each time — not itself controlled by this module).

## Main entry points

### `generate_tasks(run_id, graph, model, settings) -> list[ResearchTask]`
Calls `model.generate(..., prompt_name="research/gap_analyser.md", schema=ResearchTaskList)` with the whole graph (`graph.model_dump_json()`) as the only input — no `model_tier` argument, so it runs on the default `"fast"` tier, unlike the challenge-stage calls which explicitly use `"reasoning"`. The model can return zero tasks (the prompt says to do so when the hypothesis is already adequately supported). Results are sorted by a hardcoded `{"high": 0, "medium": 1, "low": 2}` priority map and truncated to `settings.max_research_tasks_per_cycle` (default 8) — any lower-priority overflow tasks the model proposed are silently dropped, not deferred to a later cycle.

### `retrieve_for_tasks(tasks, search, fetcher, settings, counters, guard=lambda: None) -> tuple[list[SourceRecord], list[str]]`
Pure orchestration, no LLM call. For every `search_query` on every task: calls `guard()` (a hook the pipeline wires to `self.ledger.guard_time`, i.e. a wall-clock budget check that can raise to abort the run), then checks `counters["queries"] >= settings.max_search_queries_per_run` and breaks if the run-wide query budget is exhausted. `counters` is a plain `dict[str, int]` passed in by the caller and mutated in place — this makes the query/source budget shared and cumulative across every call to `retrieve_for_tasks` within one pipeline run (i.e. across multiple research cycles), not reset per call.

For each search hit: `guard()` again, then the same budget check against `settings.max_fetched_sources_per_run` (default 50) — note this `break` only exits the *hits* loop for the current query, not the outer task/query loops, so once the source budget is hit the function keeps iterating remaining queries/tasks doing nothing useful except more `guard()` calls until they too fall through. URLs are canonicalized with `normalize_url` and deduped via an in-function `seen` set (so the same URL surfaced by two different queries is only fetched once, but this set does not persist across separate `retrieve_for_tasks` calls — a URL already fetched in a prior cycle could be re-fetched in a later one).

Failures are non-fatal and collected as strings, not exceptions: a `search.search()` exception becomes `"{query}: {exc}"`, a bad URL becomes `"{hit.url}: {exc}"`, a `fetcher.fetch()` exception becomes `"{canonical}: {exc}"` — all three are caught with a bare `except Exception`, so any failure mode (network error, `UnsafeUrl`, HTTP error, oversized page) collapses to a message string in the returned `failures` list and processing continues with the next item. `SourceRecord.id` is `f"S{counters['sources']}"` — built from the same shared counter, so source IDs stay globally unique across the whole run's research cycles, not restarted per call. `publisher` is derived from the fetched final URL's hostname (`urlsplit(...).hostname or ""`), and `suitability_reason` is a fixed-format string (`"Retrieved for task {task.id}: {task.question}"`) rather than anything the model or fetcher supplies.

### `extract_claims(run_id, tasks, sources, model, start=1) -> tuple[list[EvidenceClaim], list[RejectedClaim]]`
Builds a JSON payload of `tasks` plus `sources`, but each source's `extracted_text` is truncated to the **first 8000 characters** here — a second, tighter truncation on top of the 80,000-character cap `PageFetcher` already applies (see `providers/fetch/__init__.py.explained.md`), specific to keeping the claim-extraction prompt payload small. Calls `model.generate(..., prompt_name="research/claim_extractor.md", schema=EvidenceClaimDrafts)` — again no `model_tier`, so `"fast"` tier. The raw `EvidenceClaimDraft`s the model returns are unverified: `extract_claims` immediately hands them to `consequence_radar.evidence.verify_claims(drafts.claims, sources, start)`, which is where the actual guarantee from the prompt ("local code will reject any passage that is not an exact normalized substring") is enforced — it looks up each draft's `source_id`, normalizes both the claimed `exact_passage` and the source's full text, and rejects the draft (into `RejectedClaim`) if the source is unknown or the passage isn't found verbatim; only claims that survive get an `EvidenceClaim.id` of `f"C{start + accepted_so_far}"`. `start` lets the caller keep claim IDs unique across cycles — the pipeline passes `len(all_claims) + 1`.

## Connects to
- `consequence_radar.evidence.verify_claims` — does the actual pass/fail check on extracted claims; this module only assembles the payload and calls it.
- `consequence_radar.providers.fetch` (`PageFetcher`, `normalize_url`) — page retrieval and URL canonicalization/SSRF-guarding, imported and used directly in `retrieve_for_tasks`.
- `consequence_radar.providers.search.SearchProvider` — the `search.search(query, max_results=5)` protocol (`max_results=5` is hardcoded here, not from `Settings`).
- `consequence_radar.providers.model.ModelClient` — the `.generate()` call target for both `generate_tasks` and `extract_claims`.
- `consequence_radar.pipeline.__init__` — the sole caller. Runs a cycle of `generate_tasks` → `retrieve_for_tasks` → `extract_claims`, accumulating `all_claims`/failures across cycles, sharing one `counters` dict across the whole run's calls to `retrieve_for_tasks`.
